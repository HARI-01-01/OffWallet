# PRD: Hardware-Anchored Offline Payment System (Shadow v1)

## 1. Goal Description
The Shadow system is a **Hardware-Anchored Offline Payment Network** designed to enable secure, peer-to-peer (P2P) digital transactions without any internet connectivity. 

The core innovation is the use of a device's **Trusted Execution Environment (TEE)** or **StrongBox** (hardware security chip) to generate and store non-exportable spending keys. By binding the digital wallet to the physical hardware, we eliminate the risk of private key theft, wallet cloning, and software-based emulation.

---

## 2. Onboarding: Hardware Key Ceremony (O1-O5)

This process initializes the hardware trust anchor between the device and the server.

### 2.1 O1: Registration & Challenge
*   **Action**: User initiates registration with their name and email.
*   **Data Sent**: `RegisterRequest(wallet_name, email)`
*   **Data Received**: 
    *   `wallet_id`: Server-assigned unique identifier.
    *   `attest_challenge`: A 32-byte random nonce generated by the server.
    *   `ephemeral_server_pubkey`: Used for wrapping the local database key.
    *   `server_spki_hash`: The hash of the server's master public key (Trust Anchor).
*   **Significance**: The `attest_challenge` is critical. It must be included in the hardware attestation (O2) to prove that the spending key was generated *after* the server issued the challenge, preventing the use of pre-generated or leaked keys.

### 2.2 O2: Key Ceremony (TEE/StrongBox)
*   **Action**: The device generates an EC P-256 key pair inside the Secure Element.
*   **Properties**:
    *   `insideSecureHardware=true`: The private key never leaves the chip.
    *   `UserAuthenticationRequired`: Can be bound to biometric (fingerprint/face) unlock.
*   **Significance**: This key is the "root of spend". It is physically impossible for the user or any malware to extract this key from the device.

### 2.3 O3: Activation & Integrity
*   **Action**: Device sends proof of its hardware security to the server.
*   **Data Sent**: `ActivateRequest`
    *   `device_pubkey`: The public half of the TEE key.
    *   `attestation_chain`: A chain of certificates from the TEE to the Root CA (e.g., Google or Samsung).
    *   `integrity_token`: A Google Play Integrity verdict (attesting that the OS is not rooted/modified).
    *   `encrypted_aes_key`: A locally generated 256-bit AES key used to encrypt the local SQLite database, wrapped using the `ephemeral_server_pubkey`.
*   **Significance**: 
    *   **Attestation**: The server verifies that the key is truly in hardware and not emulated.
    *   **AES Key Wrap**: Seeds the server with a recovery-capable copy of the database key, enabling wallet recovery if the device is lost (via Shamir Shards).

### 2.4 O4: Genesis Sealing
*   **Action**: Server creates the first entry in the device's ledger.
*   **Data Received**: `Genesis` payload (signed by Server).
    *   `v`: Version.
    *   `wallet_id`: Payer's wallet ID.
    *   `device_pubkey_hash`: SHA256 of the authorized device key.
    *   `balance_p`: Initial balance (usually 0).
    *   `counter`: Initial counter (0).
    *   `genesis_epoch`: Current server epoch.
    *   `issued_at`: Timestamp.
*   **Significance**: Alice's device verifies the server's signature. This "seals" the starting state of the wallet. Alice cannot unilaterally change her starting balance.

### 2.5 O5: Security Pass Issuance
*   **Action**: Server issues a "Security Pass" defining Alice's offline spend capabilities.
*   **Data Received**: `PassEnvelope` (Signed by Server).
    *   `last_settled_head`: Hash of the last block the server knows about.
    *   `aggregate_cap_p`: Maximum amount Alice can spend offline before needing to sync (₹2,000).
    *   `txn_count_cap`: Maximum number of offline transactions allowed before sync (200).
*   **Significance**: The **Security Pass** acts as an offline "Passport". It allows Bob to trust Alice's hardware and limits without talking to the server.

## 3. Secure Top-up (Funding the Bucket)

To spend money offline, Alice must move funds from her online account to her "Offline Secure Bucket".

*   **Process**:
    1.  Alice requests a top-up of ₹X while online.
    2.  Server deducts ₹X from her online balance.
    3.  Server issues a `TopUp` payload signed with the master server key.
*   **Data Content**: 
    *   `amount_p`: The ₹ amount in paisa.
    *   `topup_seq`: A monotonic sequence number to prevent replaying old top-up signatures.
    *   `expires_at`: Expiry for the authorization.
*   **Significance**: This is a "Monotonic Lock". Alice's device will only accept a `TopUp` if the `topup_seq` is greater than the last one it processed, ensuring her balance only moves forward.

## 4. The Full BLE Payment Cycle (M1-M4)

This is the core offline protocol. It uses Bluetooth Low Energy (BLE) for discovery and high-speed data transfer.

### 4.1 Discovery: "The Handshake"
1.  **Bob (Payee)** generates a random `Session ID (sid)` and shows a QR code.
2.  **Alice (Payer)** scans the QR and obtains the `sid`.
3.  **Discovery**: Alice derives a unique **Service UUID** from the `sid` (`UUID = H(sid)`). 
4.  **Roles**: Alice starts advertising this UUID; Bob scans for it. Connection is automatic once they find the matching UUID.

### 4.2 Step 1: M1 - Payer Identification & Audit
*   **Data Alice -> Bob**: `SessionInit`
    *   `sid`: The session ID.
    *   `epk_A`: Alice's ephemeral public key (X25519) for session encryption.
    *   `chal_A`: A random challenge for Bob.
    *   `pass_A`: Alice's Security Pass (proving her limits and identity).
    *   `history_A`: A list of the last 10 `DebitBlocks` from Alice's ledger.
*   **Significance**: Bob performs a **History Audit**. He verifies that the `history_A` blocks form a continuous hash chain that terminates at the `last_settled_head` found in Alice's signed Pass. This detects if Alice has "forked" her ledger or skipped transactions.

### 4.3 Step 2: M2 - Payee Authentication & Session Binding
*   **Data Bob -> Alice**: `SessionAuth`
    *   `epk_B`: Bob's ephemeral public key.
    *   `sig_B`: Bob's hardware-backed signature over Alice's random challenge (`chal_A`).
    *   `pass_B`: Bob's Security Pass (reference).
*   **Significance**:
    1.  **Identity Binding**: Bob's signature over `chal_A` proves that the device connected via Bluetooth is the **same physical device** that showed the QR code. This prevents "Session Hijacking."
    2.  **Audit Confirmation**: Alice verifies that the `wallet_id` and `device_pubkey_hash` in `pass_B` match the data she already audited during the QR scan. **No redundant history audit is performed here.**

### 4.4 Step 3: M3 - Alice Deducts Funds (Commit)
*   **Action**: Alice's device deducts the amount from her TEE-guarded "Reserved Balance".
*   **Data Alice -> Bob**: `DebitBlock` (Hardware Signed).
    *   `prev_hash`: Hash of Alice's previous block.
    *   `amount_p`: Transaction amount.
    *   `payee_wallet_id`: Bob's ID.
    *   `payee_chal`: Bob's random challenge (proving freshness).
*   **Significance**: This block is the "Check". It is signed by Alice's hardware key. Once Bob has this, he has proof of Alice's intent to pay.

### 4.5 Step 4: M4 - Bob Finalizes (Receipt)
*   **Action**: Bob verifies the `DebitBlock`, credits his local balance, and issues a receipt.
*   **Data Bob -> Alice**: `Receipt` (Hardware Signed).
    *   `block_hash`: Hash of the `DebitBlock` he just accepted.
    *   `payee_counter`: Bob's monotonic receive counter.
*   **Significance**: Bob's co-signature on the block serves as Alice's "Receipt". Alice stores this to prove to the server that Bob actually received the money.

## 5. Synchronization & Settlement

Alice or Bob can sync their offline transactions whenever they reach internet connectivity.

### 5.1 The Sync Request
*   **Data Sent**: `OfflineSyncRequest`
    *   `transactions`: A list of `DebitBlocks` + Alice's Signature + Bob's Co-Signature (Receipt).
    *   `integrity_token`: Freshly fetched from Google Play Integrity.
*   **Significance**: The server verifies the signatures of **both** parties. If Alice tries to sync a block that Bob hasn't co-signed, it is flagged as "Doubtful".

### 5.2 Settlement Statuses
*   **SETTLED**: Server has verified the chain and both signatures. The funds are moved permanently.
*   **DOUBTFUL**: Alice claims she paid Bob, but Bob hasn't synced yet. Alice's funds stay "Reserved".
*   **AUTHORIZED_REFUND**: If Bob doesn't sync for > 24 hours, and Alice provides proof of a failed handover, the server authorizes Alice's hardware to "rollback" the funds.

## 6. Edge Cases & Security Handling

### 6.1 Double Spending Protection
*   **Constraint**: The `counter` in the `DebitBlock` must be strictly increasing.
*   **Prevention**: If Alice tries to reuse a counter, Bob's audit of her `history_A` in M1 will detect the gap or duplicate and reject the payment.

### 6.2 Communication Failure (The "Phone Died" Case)
*   **Scenario**: Alice sends M3 (Money) but Bob's phone dies before sending M4 (Receipt).
*   **Handling**: 
    1.  Alice's block is marked as "Doubtful" locally.
    2.  Alice must sync with the server to initiate a "Resolution Request".
    3.  Server waits for Bob to sync. If Bob never claims the money, Alice gets a refund.

### 6.3 Hardware Tampering
*   **Scenario**: Attacker roots the phone to read the database.
*   **Handling**: 
    1.  The database is encrypted with an AES key (DBK) stored in the TEE.
    2.  Even with root access, the attacker cannot read the database without the hardware-protected key.
    3.  `IntegrityGuardian` reports root status to the server, which then **FROZENS** the wallet on the next sync attempt.

### 6.4 Ledger Forking
*   **Scenario**: Alice tries to maintain two different "Histories" to spend the same money twice.
*   **Handling**: Since both histories must terminate at the same `last_settled_head` (signed by the server in her Pass), Alice would have to provide a valid hash chain for both. This is prevented by the monotonic hardware counter and Bob's M1 audit.
